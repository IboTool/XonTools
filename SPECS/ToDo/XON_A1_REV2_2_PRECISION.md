## 1. What the run of record and its post-hoc analysis showed (`results/a1-l1-posthoc.md`)

- **False positives.** The full engine flagged 11 of 60 consistent documents: 10 relation-judge errors (3 borderline) and 1 entity-extraction error (b31). None were unplanted contradictions. All 10 `contradicts` edges behind clause (a) flags had confidence 0.50–0.60.
- **The relation definition invited them.** Rev. 2.1's `RELATE_SYSTEM` defines `contradicts` as "impossible **or much less likely**." Several errors are the judge applying that definition to improbability (b45: pausing to sketch makes finishing ahead "less likely"; b22; b34 "assuming one folder").
- **Isolation by instruction failed.** In 8 equality-break pairs the judge reasoned through a third planted claim that was visible in the batch's claim list, despite the prompt telling it to ignore every other statement.
- **Order direction is unstable.** b31 ("Kira signed first" / "Otto signed after Kira") was normalized in opposite directions on the same attribute, closing a false 2-cycle. L1-var found the same error in b02, and entity-relation agreement across repeats was 0.518, with 32 of 54 disagreements being direction flips on `greater`.
- **Planted order relations were extracted correctly 0.900 of the time** (0.967 over all planted relations). The misses have not been classified. Every link of a cycle must be extracted for the cycle to close, so this rate compounds with cycle length.

Fixes R1 and R2 address relation scoring. Fix E1 addresses entity extraction: direction, superlatives, id consistency, coverage, and reasoning. Section 6 fixes how the confidence threshold is chosen.

## 3. Fix R1: "contradicts" means cannot both be true; a new `tension` label

### 3.1 Schema

```python
class RelationV22(BaseModel):
    a: int
    b: int
    rationale: str                     # one or two sentences, written first
    relation: Literal["supports", "contradicts", "tension", "unrelated"]
    confidence: float                  # 0..1: confidence that the label is correct
```

Field order stays rationale, relation, confidence (rev. 2.1 re-specification 13).

### 3.2 Definitions (the substance of `RELATE_SYSTEM_V2_2`)

- **contradicts:** the two statements **cannot both be true** as written. Before choosing it, look for an ordinary reading under which both hold: different times, different occasions, different objects, both things being true of different people, or loose everyday wording. If one exists, the label is not `contradicts`.
- **tension:** both can be true, but together they are surprising, awkward, or one makes the other noticeably less likely.
- **supports:** if A is true, B becomes more likely.
- **unrelated:** none of the above.
- Keep rev. 2.1's world-knowledge switch (off by default) and its wording otherwise.
- Include two short worked examples in the prompt that are **not** drawn from the L1 corpus or its topics: one pair that is `tension` rather than `contradicts` (e.g., "The road was icy." / "The courier arrived early."), one genuine `contradicts` (e.g., "The shop was closed all day Sunday." / "Ada bought bread at the shop on Sunday.").

### 3.3 How `tension` is used

- `tension` creates **no edge** in the signed claim graph. It does not enter the verdict, balance, conflict, harmony, residuals, or culprits.
- Reports list tension pairs with their rationales (`tension_pairs`), and the UI shows them in the relations table with their own color.
- The pairwise-only baseline ignores `tension`.
- Later stages (A2 onward) may use `tension` as a graded signal; that is their decision, not this one.

## 4. Fix R2: structural isolation of each pair

### 4.1 One pair per call

Relation scoring under 2.2 sends **one pair per call**. The user message contains only the two statements, labeled A and B. It contains no other claim, no claim list, no document text, and no claim numbers other than the pair's own ids (so the response can be matched). The judge can no longer see a third claim.

- **Pair selection is unchanged** (all pairs if n ≤ 25; otherwise the selection call plus a random 10% blind sample). The selection call may see the whole claim list, because it only proposes pairs and judges nothing. Its prompt and hashes are the same as rev. 2.1's, so the run of record's selections come from cache.
- **Malformed-output rule** (rev. 2.1 re-specification 14) carries over: a rationale matching `JSON_FRAGMENT`, or a response missing the pair, gets exactly one re-score call. If that is also malformed or missing, the pair stays unscored and is reported. Transport retries (timeouts, rate limits, 5xx) are not re-scores and are logged separately.
- **The 1% unscored-pair stop rule** (re-specification 15) applies unchanged.
- Relation scoring keeps thinking disabled, as in rev. 2.1.

### 4.2 Cost and throughput

Per-pair calls multiply the call count (up to 300 per document at n = 25). Before implementing:
- Check the current Anthropic documentation (https://platform.claude.com/docs) for **prompt caching** of the shared system prompt (including any minimum cacheable length) and for the **Message Batches API**. Use whichever the documentation and installed SDK support to reduce cost. Development passes may use the Batches API; the fresh recorded run's method will be decided before it runs.
- Run calls concurrently with a configurable limit, respecting rate limits.
- Cache keys still cover every request parameter actually sent. A batch-API response is cached under the same key the synchronous request would have.
- Report the measured cost per document for rev. 2.2 next to rev. 2.1's.

## 5. Fix E1: entity extraction

### 5.1 Why

Rev. 2.1 extracts the whole entity graph in one call, without thinking, and asks the model to emit `greater(a, b)` after mentally normalizing "younger", "earlier", "first", "after" to one direction. Four problems follow:
- the model chooses polarity per relation, and can choose it differently for two claims about the same attribute (b31);
- superlatives ("Kira signed first") have no representation, so the model turns them into pairwise relations with a partner the claim doesn't name;
- nothing stops two ids for one entity or attribute within a document, and a cycle cannot close across two keys;
- nothing checks that every claim stating an order produced a relation.

Under 2.2, extraction runs in steps (5.2), ids are constrained by the schema (5.3), the model **transcribes** what each claim says while code **derives** direction (5.4–5.5, 5.8), a deterministic coverage net catches missed order claims (5.6), and the extraction calls reason before answering (5.7).

### 5.2 Steps

Per document, after claim extraction:
1. **Inventory call** (`ENTITY_INVENTORY_SYSTEM_V2_2`): given the numbered claims, list the entities (merging mentions that refer to the same entity) and the attributes on which entities are compared, with arity and `order_kind` (5.3).
2. **Relations call** (`ENTITY_RELATIONS_SYSTEM_V2_2`): given the numbered claims and the inventory, emit same/different relations, order statements, extreme statements, and comparative senses. The schema for this call is built from the inventory (5.3).
3. **Coverage check** (deterministic, 5.6), with at most one follow-up call (`ENTITY_COVERAGE_SYSTEM_V2_2`).

### 5.3 Schemas, with ids constrained per document

```python
class AttributeV22(BaseModel):
    key: str
    arity: Literal["binary", "multi", "unknown"]
    arity_span: str | None
    order_kind: Literal["sequence", "magnitude", "other"] | None
        # sequence: an order in time or position (arrival, finishing, signing up); greater = LATER
        # magnitude: an amount (age, height, weight, score); greater = MORE
        # other: any order not clearly one of these (e.g. rankings); greater = defined by `other_greater_means`
        # None: the attribute has no order statements
    other_greater_means: str | None    # required iff order_kind == "other", e.g. "a better (numerically lower) rank"

class InventoryV22(BaseModel):
    entities: list[Entity]             # rev. 2.1's Entity: id, mentions
    attributes: list[AttributeV22]
```

The relations call's schema is **generated per document** from the inventory, so that every entity field accepts only the inventory's entity ids, every attribute field only its attribute keys, and every `claim_id` only the document's claim ids (for example with `pydantic.create_model` and `Literal[...]` over the ids, or JSON-schema `enum`). The model therefore cannot introduce a new or variant id mid-document. Check the structured-output documentation and the installed SDK for limits on enum size and schema complexity; if a document exceeds them, report it and fall back to validating ids after the call, with invalid ids counted as unextracted relations.

```python
class OrderStatement(BaseModel):       # "Otto signed after Kira."
    claim_id: ClaimId
    attribute: AttributeKey
    subject: EntityId                  # the claim's grammatical subject of the comparison ("otto")
    comparative: str                   # verbatim word or phrase from the claim ("after")
    object: EntityId                   # the entity compared against ("kira")
    confidence: float

class ExtremeStatement(BaseModel):     # "Kira signed first."
    claim_id: ClaimId
    attribute: AttributeKey
    entity: EntityId
    comparative: str                   # verbatim ("first")
    restriction: str | None            # verbatim qualifier limiting the comparison set, if any
                                       # ("of the judges", "on the team", "to the café"); None if unrestricted
    confidence: float

class ComparativeSense(BaseModel):     # one per distinct (attribute, comparative)
    attribute: AttributeKey
    comparative: str
    greater_side: Literal["subject", "object", "max", "min"]
        # subject/object for OrderStatement comparatives; max/min for ExtremeStatement comparatives,
        # relative to the attribute's canonical direction

class EntityRelationsV22(BaseModel):
    same_different: list[EntityRelation]      # kind in {"same", "different"} only; rev. 2.1 semantics
    orders: list[OrderStatement]
    extremes: list[ExtremeStatement]
    senses: list[ComparativeSense]
    unsupported_order_claims: list[ClaimId]   # claims stating an order that cannot be represented (5.4)
```

### 5.4 Instructions for the relations call

`ENTITY_RELATIONS_SYSTEM_V2_2` instructs the model to:
- copy `comparative` verbatim from the claim, and use the claim's own grammatical subject and object, never swapping them to normalize;
- give exactly one `ComparativeSense` per distinct (attribute, comparative) pair, so a word cannot receive two directions within a document;
- record any qualifier that limits a superlative's comparison set verbatim in `restriction`;
- not emit an order statement for a negated or hedged comparative ("not before", "maybe after"), and list such claims in `unsupported_order_claims`;
- not infer relations or superlatives a claim does not state (rev. 2.1's rule, kept).

### 5.5 Deterministic lexicon (`xon/llm/comparatives.py`, standard library only)

A fixed table of unambiguous comparatives for `sequence` and `magnitude` attributes, matched case-insensitively on whole words after trimming:

| order_kind | greater_side = subject | greater_side = object | max | min |
|---|---|---|---|---|
| sequence (greater = later) | after, later than, behind, followed | before, earlier than, ahead of, preceded, prior to | last, final | first, earliest |
| magnitude (greater = more) | older, taller, heavier, larger, bigger, longer, more, higher | younger, shorter, lighter, smaller, less, fewer, lower | oldest, tallest, heaviest, largest, biggest, longest, most, highest | youngest, shortest, lightest, smallest, least, fewest, lowest |

Rules:
- When the lexicon covers a comparative on an attribute of kind `sequence` or `magnitude`, **the lexicon's sense is used**. If the model's sense disagrees, log it in the diagnostic `sense_overrides`.
- Comparatives the lexicon doesn't cover, and every attribute of kind `other`, use the model's sense.
- Rank words ("ranked higher", "placed above") are deliberately absent: they are ambiguous between rank number and standing.
- The table may be extended only by a logged decision, never in response to a specific document's result.

### 5.6 Coverage net

After the relations call, for each claim (any kind), search its text for the lexicon's words and phrases (whole words, case-insensitive). A claim that contains one is **covered** if it appears as the `claim_id` of at least one order statement, extreme statement, or same/different relation, or is listed in `unsupported_order_claims`. Otherwise it is **uncovered**.

If any claim is uncovered, make **one** follow-up call (`ENTITY_COVERAGE_SYSTEM_V2_2`) per document, listing only the uncovered claims, with the same inventory and the same per-document schema, plus for each listed claim an explicit `none` option with a one-sentence reason (many matches are not relational: "for the first time", "more people came"). Merge its statements into the document's extraction. There is no second follow-up. Claims still uncovered are reported.

The net only adds statements; it never removes or edits anything from the relations call. It applies identically to every document and is decided from the text alone, before any analysis.

### 5.7 Thinking for the entity calls

The inventory, relations, and coverage calls run with **adaptive thinking at default effort**. Claim extraction and relation scoring stay without thinking, as in rev. 2.1. `max_tokens` for these calls must cover thinking plus output. Verify against the documentation that thinking is compatible with the structured-output method in use; if it is not, report before implementing an alternative.

### 5.8 Derivation into the existing entity graph

- An `OrderStatement` with `greater_side = subject` becomes `greater(subject, object)`; with `object`, `greater(object, subject)`. Confidence and claim id carry over.
- An **unrestricted** `ExtremeStatement` with `max` on entity E becomes `greater(E, X)`; with `min`, `greater(X, E)`. Here X ranges over every other entity that appears in any order statement or unrestricted extreme statement on the same attribute, **excluding entities in E's equality class**. Each derived edge keeps the extreme statement's claim id and confidence and is marked `derived_from_extreme`. Expansion is therefore bounded by the document's own order statements on that attribute.
- A **restricted** `ExtremeStatement` (non-null `restriction`) is not expanded. It is listed under `restricted_extremes` and reported. It cannot produce a contradiction under 2.2.
- Two distinct entities both `min` (or both `max`) on one attribute, both unrestricted and not in the same equality class, produce a directed 2-cycle through the existing order-cycle check (a **superlative collision**). Report it with contradiction type `superlative_collision`, listing both claims.
- `same`/`different`, equality classes, binary parity, and order-cycle detection (rev. 2.1, Section 4.7) are unchanged and run on the derived edges.

## 6. The confidence threshold: a selection rule fixed in advance

Rev. 2.1 uses τ = 0.5 for all clauses and the pairwise baseline. The value was a default, not a calibrated choice. Rev. 2.2 selects τ by the following rule, applied once, on the final development pass (Section 7):

1. For each method with a threshold (full engine, minimal engine, pairwise-only), compute direct F1 and cycle F1 on the 180 development documents for τ ∈ {0.50, 0.55, 0.60, …, 0.90}.
2. Select, **per method**, the τ that maximizes the mean of direct F1 and cycle F1. Ties go to the lowest τ.
3. One τ per method applies to every clause of that method (clauses (a), (b), (c) for the engine; (a) and (c) for the minimal engine).
4. Record the selected values in `config.py` as `relation_threshold_v2_2` per method, and freeze them with the prompts.

Also report, labeled **report-only**, the same curves for rev. 2.1 computed from the run of record's cache (no API calls, no change to its results). The LLM-direct baseline has no threshold and is unaffected.

## 7. The development pass

### 7.1 Step 0: classify the missed planted order relations (no API calls)

Before implementing Fix E1, classify every planted order relation in the run of record that the L1 diagnostic counted as not extracted correctly (seed 0), by reading the cached extraction and the document:
- **direction flip:** the right entities and attribute, the wrong direction;
- **id mismatch:** the relation exists, but under a variant entity id or attribute key, so it cannot join the rest of the cycle;
- **not extracted:** no relation from the claim;
- **wrong relation:** a different kind or different entities;
- **scoring artifact:** the extraction would close the planted cycle in the engine, but the diagnostic's matching rule counted it as wrong.

## 11. What the results would and would not mean

- **Fewer false positives on the development set** would show the fixes remove the error types the post-hoc analysis found. It would **not** show the engine's false-positive rate on new text, because the fixes were designed after reading these errors. That number comes only from the fresh corpus.
- **Higher order-relation accuracy** matters beyond L1: every link of a cycle must be extracted for the engine to see it, so accuracy compounds with cycle length (at 0.90 per link, an eight-link cycle survives about 43% of the time). Step 0's classes show which fix moved which errors.
- **Higher entity agreement in L1-var** would show that deriving direction in code and constraining ids remove the instability. It would be measured on 12 documents: a strong signal, but a small sample. A2 does not use the entity graph; what carries into A2 from this revision is R1 and R2.
- **Lost direct detections labeled `tension`** would mean the new definition is too strict for some genuine contradictions. That tradeoff should be read in the numbers, not tuned away on this corpus.
- **Superlative collisions** are a new detection path. On this corpus they can only add false positives or confirm planted order contradictions; their value is tested on the fresh corpus.
- **The pairwise baseline is expected to weaken further on cycle documents**, because contamination supplied most of its equality-break detections. That makes the comparison with the engine more honest, not the engine better.
- **None of this bears on the Xon model.** These are fixes to LLM-assisted extraction and a classical consistency check.
