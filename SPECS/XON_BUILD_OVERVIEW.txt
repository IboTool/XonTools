============================
Updated: September 25, 2026 (A1 rev 2.2 specified; repository under git)

harmonic architecture is pursued for what it can do, and each stage has to beat
a simple baseline to earn its place. The Xon's metaphysics is not part of this
build.

EARLIER (after the scouting runs)
  Three scouting runs (docs/scouting/RESULTS_*.md) settled the harmonicity
  question for now:
    - Frequency-group "rich coherence" rewards fragmentation, and locking and
      coherence metrics are blind to inconsistency. It is not a usable
      objective.
    - The defensible form of harmony is NORMALIZED FRUSTRATION ENERGY WITH
      EVIDENCE CLAMPED. It tracks inconsistency, recovers the truth from sparse
      evidence, and resists freezing, but it rewards three rule-breaks
      (dropping evidence, cutting relations, rewriting evidence), so guards
      are requirements.
    - Computed exactly (A1), it is reliable. Computed by an oscillator field,
      it gets stuck in twisted states (6% of runs at 25% evidence, 32% at 10%).
    - As a drift detector, the field lost to spectral-CUSUM.
  So: the exact solve is the meter; the field matters only as continuous
  dynamics for agents, and its reliability is what the H track now tests.

The project runs on two tracks that meet in the convergence stages.

  TOOLS TRACK (A)        consistency engine -> agent monitor ->
                         learning core -> coherence-driven agent
  HARMONICITY TRACK (H)  the field as consistency dynamics: can it be made
                         reliable, and does coarse-to-fine growth help?
  CONVERGENCE (C)        C2  drift detector (spectral-CUSUM on monitor traces)
                         C1  belief sheaf + field as one system (deferred)
  OPTIONAL (A5)          a language model trained with local learning

Every spec is written as a direct prompt for Cursor (or Claude Code). Hand the
coding agent the whole file, and have it run `pytest` plus the stage's eval CLI
before declaring the stage done. Every stage runs offline from fixtures.

PRINCIPLES
---------------------------------------------------------------------------------
  - Two ledgers. Pre-registered experiments test claims; thresholds are fixed
    before running and changes are logged with reasons. Search (H2) finds
    configurations that work; those are existence results, never model
    predictions.
  - Negative results stay on the record.
  - Every experiment has a control or baseline, and the field must beat the
    simple baseline on the same signal before it is called a tool.
  - Evidence is clamped wherever the architecture reasons: beliefs may change,
    observations may not.
  - What gets clamped is a SECURITY decision: only trusted sources. Content an
    attacker could write is a claim, never evidence.
  - Any quantity used as an OBJECTIVE passes an exploit battery first
    (fragmentation, freezing, death, noise, frustration, balanced control, and
    the rule-breaking levers).
  - Reliability is set by PROVENANCE, never by fit to current beliefs.
  - What gets clamped is decided by provenance, never by wording.
  - A monitor never fails silently: when its assurance checks fail, it says
    "could not assess", never "not flagged".
  - The tools' own prompts are defended against injection by the text they read.
  - Explanations are for humans; automated pipelines get verdicts only.
  - Evidence integrity is checked, not assumed: trusted evidence is hash-chained
    at capture, and a broken chain downgrades later evidence to untrusted. A hash
    proves integrity, not trustworthiness.
  - Measurement uses exact computation where it exists; dynamics are used only
    where continuity is the point, and only with a validated schedule.
  - Monitor and detector outputs are never used to train a monitored agent.
  - When a pre-registered criterion needs re-specifying, the question is asked
    WITHOUT running it or showing predicted outcomes; it runs after the choice.
  - The API key lives only in the environment.
  - Each spec ends with what its results would and would not mean.
  - Test-case verification never uses the system being evaluated: ground truth
    comes from structure (solvers, scripted harnesses), and the engine never
    screens its own test corpus.
  - A reviewer's clean result counts only if it caught a known defect.
  - A seen corpus becomes a development set: fixes may be developed and
    iterated on it (each iteration logged and counted), but results of
    record come only from a fresh, sealed corpus, run once after a freeze.
  - Thresholds on model confidences are chosen by a rule fixed before the
    development data is seen, never by where known errors sit.
  - What a model must not use, it must not see: isolation is enforced by
    what the prompt contains, not by instructions.
  - Where a deterministic rule exists (direction, units, ids), models
    transcribe and code derives.
  - The repository is committed at each logged step; freezes and runs of
    record are tagged; pushed history is never rewritten.
